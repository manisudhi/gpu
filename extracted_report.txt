Abstract
Antimicrobial resistance (AMR) creates a growing need for computational methods that can compare large numbers of resistance profiles, identify recurring patterns, group similar records, and highlight unusual observations. This project proposes a GPU-accelerated AMR analysis system designed for Apple Silicon hardware, specifically the MacBook Air M3, using Apple Metal and Metal Compute Shaders. The system treats AMR records as numerical feature vectors and develops a CPU sequential implementation as a baseline before moving computationally intensive operations to the GPU.
The central GPU workload is parallel similarity computation: independent records or feature comparisons can be evaluated concurrently by thousands of GPU threads. The same feature representation can also support K-means clustering and distance-based anomaly detection. A branching architecture is used so that the preprocessed feature matrix feeds both a CPU reference path and a GPU/Metal path. Their outputs are then integrated for correctness checking and performance evaluation. Execution time, throughput, speedup, and scalability are used to assess the benefit of parallel execution.
The project is designed as an analytical and performance-comparison system rather than a clinical diagnostic tool. Expected outcomes include faster processing for sufficiently large workloads, reproducible AMR similarity and grouping results, and a clear demonstration of when GPU parallelism is advantageous and when overhead may dominate.

1. Introduction
Antimicrobial resistance occurs when microorganisms such as bacteria, viruses, fungi, or parasites change over time and no longer respond effectively to medicines intended to treat them. AMR surveillance produces structured records containing information such as organism, antibiotic, geographic or institutional context, year, and a resistance-related measurement or category. When these records become large, repeated comparisons and statistical operations can require substantial computation.
This project focuses on the computational side of AMR analysis. Rather than building a medical decision system, it develops a parallel-processing pipeline that can transform AMR observations into feature vectors and execute repeated numerical calculations efficiently. The GPU is therefore a computational engine: it performs many independent distance, similarity, assignment, or scoring operations concurrently.
The implementation targets the Apple MacBook Air M3. Because the M3 uses Apple Silicon, the project uses Apple's Metal framework and Metal Shading Language rather than CUDA. The host application prepares data and dispatches kernels, while the GPU executes the parallel kernels over feature matrices and result buffers.
2. Problem Statement
A conventional sequential AMR analysis pipeline processes records one operation at a time on the CPU. For small datasets this is practical, but repeated pairwise comparisons, distance calculations, clustering assignments, and anomaly scores can become increasingly expensive as the number of records and features grows.
The project addresses the following problem: how can computationally intensive AMR pattern and similarity operations be redesigned as data-parallel workloads and executed efficiently on an Apple Silicon GPU, while preserving correctness and providing a measurable CPU-versus-GPU performance comparison?
3. Aim
To develop a GPU-accelerated antimicrobial resistance analysis system that uses Apple Metal Compute Shaders to parallelize similarity detection, clustering, and anomaly-oriented computations, and to evaluate the performance and scalability of GPU execution against a CPU sequential baseline.
4. Objectives

Implement a CPU reference version of the main analytical operations.

5. Motivation
The project is motivated by the intersection of two needs: AMR surveillance requires computational comparison of heterogeneous records, and modern GPUs are designed to execute large numbers of similar numerical operations concurrently. A successful implementation demonstrates practical GPU programming on consumer Apple Silicon hardware rather than relying on a dedicated CUDA workstation.
The project also provides an educational contribution: the same data can be processed through a sequential CPU path and a parallel GPU path, making the effect of parallelization measurable. The architecture exposes where GPU acceleration helps and where data transfer, kernel launch, or small workload overhead can limit gains.
6. Existing System
Primarily CPU-based sequential processing.
Similarity calculations are performed record by record or through conventional vectorized CPU routines.
Clustering and anomaly calculations may be executed on the CPU without explicit GPU kernel design.
Performance is often reported as analytical output rather than as a detailed CPU-versus-GPU benchmark.
Visualization may be separated from the computational pipeline.
7. Proposed System
The proposed system introduces a branching architecture. AMR data first passes through ingestion, validation, preprocessing, and feature encoding. The resulting feature matrix then feeds two computational paths: a CPU sequential baseline and a GPU path implemented with Metal Compute Shaders. The GPU path can branch into similarity detection, K-means clustering, and anomaly detection. Results from these branches are integrated and compared with the CPU reference before visualization and reporting.

The exact dataset should be documented in the implementation report with its source, number of records, feature definitions, missing-value policy, and preprocessing decisions.

Synthetic expansion must not be presented as additional real-world AMR observations.

13. CPU Baseline Implementation
The CPU baseline should prioritize correctness and reproducibility. For each operation, the CPU loops through records and computes the same mathematical quantity later executed by the GPU. The baseline time should include the computational work but should be measured consistently with the GPU experiment.
13.1 CPU Similarity Logic
For a query vector q and record vector x, a simple distance can be Euclidean distance: d(q,x) = sqrt(sum_i (q_i - x_i)^2). Cosine similarity may be used when direction rather than magnitude is more meaningful. The selected metric must be stated clearly and used consistently.
13.2 Why the CPU Baseline Matters
The baseline is the correctness oracle for the project. GPU acceleration is meaningful only if the parallel implementation produces equivalent results within an explicitly stated numerical tolerance.
14. GPU Implementation Using Apple Metal
Metal provides low-level access to the Apple GPU through command queues, buffers, pipeline states, and compute encoders. A compute shader is compiled into a compute pipeline state and dispatched over a grid of threads. The project maps independent AMR calculations to these threads.
14.1 GPU Data Flow
The host prepares a contiguous feature matrix, creates GPU buffers, binds buffers to the compute pipeline, dispatches the kernel, and waits for completion. The result buffer is then read or synchronized for host-side evaluation. For repeated workloads, buffer reuse can reduce allocation overhead.
14.2 Thread Mapping
A simple mapping assigns one GPU thread to one record for a query-based similarity calculation. The global thread identifier selects the record index. Each thread reads the record's feature values, computes the score, and writes one result value. This avoids inter-thread dependencies in the core scoring operation.

16. AMR Similarity Analysis
Similarity analysis is the central GPU workload. After preprocessing, each AMR record is represented by a feature vector. Given a query profile, the system calculates a distance or similarity score between the query and many records. These comparisons are independent and therefore suitable for data-parallel execution.
Figure 3. Parallel AMR similarity analysis workflow.
A practical implementation can return the top-k most similar records rather than storing every pairwise score. For a full all-pairs similarity matrix, memory requirements increase rapidly with record count, so tiled or batched approaches may be preferable.
17. GPU-Based Clustering
K-means clustering partitions feature vectors into K groups by alternating between assignment and centroid-update stages. The assignment stage is especially GPU-friendly: each record can independently compute its distance to every centroid and select the closest one.
A simplified iteration is: (1) assign each record to its nearest centroid; (2) accumulate feature sums and counts per cluster; (3) update centroid coordinates; and (4) repeat until convergence or a maximum iteration count is reached. Reduction operations in the centroid-update stage require more careful synchronization than the independent assignment stage.
18. Anomaly Detection
The project can use a simple distance-based anomaly score. After clustering, a record's distance from its assigned centroid can be treated as a measure of how unusual the record is relative to its cluster. Records above a chosen threshold become anomaly candidates. The threshold should be selected from a documented statistical rule or validation procedure rather than arbitrarily changed to produce attractive results.
An anomaly flag is an analytical indication, not a clinical conclusion. It should be interpreted as a prompt for further inspection of the underlying record, data quality, or epidemiological context.

22. GPU Architecture and Execution Model
The GPU execution model separates host responsibilities from device responsibilities. The host controls data preparation, Metal resources, command encoding, dispatch, synchronization, and result retrieval. The GPU executes the compute shader across many threads. The design aims to maximize useful arithmetic per memory access while minimizing unnecessary host-device synchronization.
22.1 Main GPU Components
Host CPU: prepares data and controls the Metal command pipeline.
Metal buffers: hold feature matrices, labels, centroids, scores, and intermediate values.
Compute pipeline state: represents the compiled Metal compute shader.
Compute encoder: binds buffers and configures dispatch.
Threadgroups: organize GPU threads for efficient scheduling.
Compute threads: perform independent record-level calculations.
Result buffers: store scores, cluster assignments, or anomaly values for retrieval.

23. Algorithms and Pseudocode
23.1 CPU Similarity
FOR each record x in dataset:    distance = 0    FOR each feature i:        diff = query[i] - x[i]        distance += diff * diff    score[x] = sqrt(distance)RETURN score
23.2 GPU Similarity Kernel
thread_id = global_thread_id()IF thread_id < number_of_records:    x = feature_matrix[thread_id]    distance = 0    FOR each feature i:        diff = query[i] - x[i]        distance += diff * diff    result[thread_id] = sqrt(distance)
23.3 K-means Assignment
FOR each record x in parallel:    best_cluster = 0    best_distance = distance(x, centroid[0])    FOR k = 1 to K-1:        d = distance(x, centroid[k])        IF d < best_distance:            best_distance = d            best_cluster = k    assignment[x] = best_cluster

25. Expected Results
The system should produce reproducible similarity scores for AMR feature vectors.
K-means should group records into clusters based on the selected feature representation.
The anomaly module should identify records that are unusually distant from their assigned cluster or reference profile.
GPU results should agree with the CPU reference within a documented numerical tolerance.
For sufficiently large parallel workloads, the GPU path is expected to reduce computation time, although small workloads may show limited benefit because of dispatch and memory overhead.
The benchmark should reveal a workload size at which GPU acceleration becomes more useful and should quantify that crossover experimentally.
26. Advantages
Uses the integrated GPU already available on Apple Silicon hardware.
Demonstrates genuine GPU computation rather than GPU-only visualization.
Provides a CPU reference path for correctness validation.
Supports similarity, clustering, and anomaly-oriented analysis from a common feature matrix.
Can scale computational workload independently from the original dataset through controlled benchmark expansion.
Provides measurable performance metrics suitable for a GPU programming project.
27. Limitations
GPU acceleration is workload-dependent; small datasets may not benefit because of kernel-launch and memory-management overhead.
The MacBook Air M3 is a fanless consumer system, so sustained workloads may be affected by thermal behavior.
AMR datasets can contain missing values, inconsistent coding, sampling bias, and heterogeneous measurement conventions.
Similarity and anomaly scores depend strongly on feature engineering and the selected distance metric.
Clustering results depend on K, initialization, feature scaling, and convergence criteria.
The system is an analytical prototype and is not intended to make clinical treatment decisions.

29. Conclusion
This project proposes a practical GPU programming solution for antimicrobial resistance pattern analysis and similarity detection on Apple Silicon. The key design decision is to treat repeated AMR numerical calculations as data-parallel workloads and implement them with Apple Metal Compute Shaders. The system begins with a common data source and preprocessing stage, branches into CPU and GPU execution paths, further divides GPU computation into similarity, clustering, and anomaly workloads, and finally converges results for performance evaluation and reporting.
The project is technically feasible on a MacBook Air M3 and provides a clear opportunity to demonstrate parallel computing concepts including thread mapping, buffer management, kernel dispatch, synchronization, numerical validation, and performance measurement. The final experimental conclusions should be based on measured results rather than assumed speedups. This makes the project both technically credible and suitable for an academic GPU programming submission.
